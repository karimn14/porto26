Battery Modeling for Embedded Apps

// SOC the cheap way

My ESP32 datalogger died at 47% battery — according to firmware. Real terminal voltage was 3.1 V. Coulomb counting had drifted by half a charge cycle. OCV lookup was two hours stale. Both methods alone lie. Together, they almost stop lying.

Bench shot— single 18650, electronic load, ESP32 + INA219 logging via UART.

01 / The lying battery

The datalogger was supposed to nap, wake every five minutes, sample, log to SD, sleep. A 2000 mAh 18650 cell should have powered it for two weeks. It lasted four days. Worse, the on-board "battery percentage" cheerfully reported 47% when the cell was actually almost flat.

The problem wasn't the battery. It was that I was running two state-of-charge estimators, both wrong in different ways, and trusting whichever one was friendlier.

Fig. 01— Measured OCV(SOC) for a generic 3000 mAh NMC 18650 at 25 °C. Step relaxation visible at every 10% rest point.

02 / The two flavors of wrong

Most embedded battery monitors do one of two things:

OCV lookup (open-circuit voltage). Wait until the battery is resting, measure terminal voltage, look up SOC from a precomputed curve. Pro: no drift. Con: requires a long, undisturbed rest (often > 30 min) for the cell to actually reach OCV. In a real product, that rest almost never happens.

Coulomb counting. Integrate current in and out: SOC -= I·Δt / Capacity. Pro: instantaneous and responsive. Con: drifts. The ADC offset, the current shunt tolerance, leakage you didn't measure, self-discharge during sleep — they all integrate too.

Run either alone for two weeks and watch the lie compound. Run both and arbitrate: that's where it gets interesting.

03 / The 1st-order equivalent circuit model

Every academic SOC paper starts from the same equivalent circuit. The simplest useful version (Thévenin with one RC pair):

V_terminal(t) = OCV(SOC) − I(t)·R0 − V1(t)
dV1/dt        = −V1/(R1·C1) + I(t)/C1
dSOC/dt       = −I(t) / (3600·Q_nom)

Three component values to find: R0 (instant IR drop), R1 + C1 (slower transient — diffusion, polarization). Their ranges for a healthy 18650 at 25 °C:

  • R0 ≈ 30–80 mΩ
  • R1 ≈ 10–40 mΩ
  • C1 ≈ 1,000–10,000 F (yes, kilo-farads — long time constants)

OCV(SOC) is a curve, not a constant. For Li-ion NMC chemistry it's gently sloped (about 0.5–1 mV per percentage point in the middle of the range). For LiFePO4, it's almost flat across 20–80% — which is why pure OCV estimation is hopeless on LiFePO4 and why coulomb counting is mandatory there.

04 / Try this yourself — fit the model to a real cell

You need a single 18650 cell, a constant-current discharger (an electronic load, or a USB load with a known resistor), a multimeter or ESP32 + INA219, and a few hours.

  1. Charge the cell to 4.2 V, rest 30 min. Record OCV.
  2. Discharge at constant 0.5 C (about 1.5 A for a 3000 mAh cell). Log terminal voltage and current at 1 Hz.
  3. Every 10% capacity removed, pause discharge for 30 min. Record OCV at end of rest — that's your OCV(SOC) point.
  4. From the voltage step at the instant of load application: R0 = ΔV_instant / I.
  5. From the slower voltage relaxation after load removal: fit V1(t) = V1₀ · exp(−t/τ) to get τ = R1·C1. Pick a C1 guess (~3,000 F) and solve for R1.

You'll have ten OCV points, one R0, one R1·C1 pair. That's a usable first-order model — enough to write a hybrid estimator that doesn't lie.

05 / The hybrid estimator that mostly works

The pragmatic answer is: coulomb-count continuously, correct from OCV during idle. The trick is detecting idle robustly.

// every loop, dt = elapsed seconds
float i = ina219_read_current();   // signed, +charge / -discharge
float v = ina219_read_voltage();

// 1. coulomb-count
soc -= (i * dt) / (3600.0f * capacity_Ah);

// 2. low-current idle detector
if (fabsf(i) < 0.05f) {            // 50 mA threshold; tune to your load
    idle_seconds += dt;
} else {
    idle_seconds = 0;
}

// 3. correct from OCV after a long rest
if (idle_seconds > 300.0f) {       // 5 min idle ≈ near-OCV
    float soc_ocv = lookup_ocv_table(v);
    soc = 0.90f * soc + 0.10f * soc_ocv;  // gentle blend
}

// 4. clamp
if (soc > 1.0f) soc = 1.0f;
if (soc < 0.0f) soc = 0.0f;

The gentle blend keeps coulomb-counting responsive while letting OCV correct slow drift. Tune the threshold (50 mA), idle window (5 min), and blend factor (10%) to your application.

Fig. 03— Hybrid estimator vs. coulomb-only vs. OCV-only over a 72-hour mixed-load test. Hybrid stays within 4% true SOC, coulomb-only drifts to 18% after 48 hours.

06 / When you actually want an EKF

The hybrid above is good to about 5% SOC error. Battery management ICs (BQ27441, MAX17048, etc.) do better — typically 1–2% — using extended Kalman filtering and proprietary OCV-impedance models. If you're shipping a product, just buy the IC.

If you're learning or constrained to bare-metal, the EKF version is genuinely satisfying to implement. Plett's free Coursera course from CU Boulder walks through it in three hours. The math reduces to a 2-state filter (SOC, V1) — small enough to run at 1 Hz on a Cortex-M0.

07 / What I still don't know

I haven't characterized cell aging. R0 grows roughly linearly with cycle count, but the rate depends on temperature history and depth-of-discharge profile. There's a battery aging field note in this somewhere — once I have logs from a cell I've cycled deliberately for a few hundred runs.
