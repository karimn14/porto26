02Approach

We split the problem into three coupled subsystems: flight control, perception, and payload. Each was prototyped against simulation before any field test.

  • Flight stack — Pymavlink/MAVSDK on Jetson Nano, ArduPilot on Pixhawk 2.4.8. ROS Noetic ran in parallel as the validation harness, not the primary control path.
  • Perception — Custom YOLOv11 model on the Jetson, trained on canopy imagery, achieving 92% mAP@50 at real-time framerate for obstacle and target detection.
  • Payload — STM32-based actuation board with a FastAPI bridge for ground-station telemetry and remote commands.

Why ROS as a validator, not a controller

We kept ROS off the critical flight path on purpose. ROS pubsub adds latency we can't bound; MAVLink over serial is bounded and deterministic. ROS shines in SITL/HIL where we want to replay logs, swap simulators, and feed in synthetic sensor noise.

void on_telemetry_command(cmd_t c) {
    switch (s) {
        case IDLE:    if (c == ARM_REQ)  s = ARM; break;
        case ARM:     if (c == FIRE)     s = DISCHARGE; break;
        case DISCHARGE: timer_start(150);  s = COOLDOWN; break;
        case COOLDOWN:  if (timer_elapsed()) s = IDLE; break;
    }

07Lessons

  • Don't let ROS into the hard real-time loop. Use it where it earns its keep — replay, validation, sim.
  • Build the digital twin before you fly. Every hour in sim saves a day in the field.
  • Operator UX matters more than you think. The ground-station dashboard caught two bugs that pure logs would have missed.
